# 城内工坊 2.5D 编辑器改造路线图

## 背景

当前城内工坊的沉浸式编辑器用 React DOM/SVG 直接表达 2.5D 地图。它可以快速出效果，但地板、墙板、门框和机关附着物被包在同一个格子级 DOM 层里，导致遮挡只能按整格排序，无法表达真实的局部物理关系。典型问题是地板整体压住墙板，墙板也无法稳定地遮挡或被地面附着物遮挡。

上线后的核心需求不是多人同时编辑同一张地图，而是模板可分享、可继承、可在不同用户之间传递并各自改进。因此改造重点是稳定的数据模型、可靠的单客户端编辑体验、明确的模板来源/继承关系，以及后续替换渲染核心时不破坏旧模板。

## 目标

- 保留现有 React 页面、模板库、工具栏、保存入口和白通路校验。
- 建立稳定的城内通道领域模型，明确地板、墙、门框、机关、连接点的占位、挂载面和遮挡语义。
- 让旧模板、草稿和本地模板继续可读可编辑。
- 为后续 PixiJS 渲染核心提供清晰的渲染项输入，而不是让渲染器反推业务含义。
- 支持模板分享、复制、二次编辑和来源追踪。

## 非目标

- 不做多人同时编辑同一模板的协同协议。
- 不把整个工坊页面推倒重写。
- 不在第一阶段引入 PixiJS 或重做所有视觉效果。
- 不改变白通路校验的行为语义，除非后续阶段明确需要。

## 总体架构

React 继续负责页面框架、面板、按钮、模板库、保存和校验。地图核心逐步收敛为三层：

1. **领域模型层**：从存档数据生成规范对象，描述物件的占位、挂载面、阻挡关系、渲染语义和模板来源。
2. **渲染适配层**：把领域对象拆成可排序的物理渲染项，例如地面基座、地面附着物、墙面、墙面附着物、门框主体、连接点。
3. **渲染执行层**：短期仍可用 DOM/SVG，长期替换为 PixiJS，React 只把状态传给画布核心。

排序设计参考了成熟 2D/2.5D 工具的通用做法：PixiJS 通过容器的 `zIndex` 和 `sortableChildren` 控制同级对象绘制顺序；Godot 的 2D `CanvasItem` 支持 `z_index` 与按 Y 坐标排序；Tiled 对 object layer 提供 `draworder`，可按出现顺序或 Y 坐标绘制。结论是：编辑器数据可以保持模板和物件的逻辑组织，但实际绘制必须拆成同级 render item，并用投影深度与物理层级共同排序。
