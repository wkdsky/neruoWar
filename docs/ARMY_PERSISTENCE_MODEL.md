# 部队持久化模型

## 数据边界

兵种目录与玩家部队分开保存：兵种目录是全局静态定义，玩家数据只保存对目录的引用和可变状态。

| 数据 | 存储位置 | 含义 | 是否消耗真实士兵 |
| --- | --- | --- | --- |
| `ArmyUnitType` | 兵种目录集合 | 兵种属性、组件、每名真实士兵的 `costKP` | 否 |
| `User.armyRoster` | 用户文档 | 账号拥有的真实士兵总量 | 账号总账 |
| `User.armyTemplates` | 用户文档 | 配比为 100% 的模板与阵型 | 否 |
| `User.combatArmies` | 用户文档 | 根据模板编成的实际参战部队 | 是，作为已占用份额 |
| `User.trainingArmies` | 用户文档 | 训练场的我方/敌方训练部队及其摆放状态 | 否 |

`combatArmies` 和 `trainingArmies` 都保存独立的兵种数量、名称、模板阵型快照、当前阵型、技能槽、坐标与放置状态。因此后续编辑或删除模板，不会篡改已经创建的部队实例。

这是游戏中常见的“静态定义 / 编队模板 / 玩家持有实例”分层：兵种目录可被所有玩家复用，模板只保存意图，实例保存真正可参战或训练的状态。当前每名玩家的模板和编组数量有明确上限，因此将它们嵌入 `User` 文档可以一次读写该玩家的完整军队状态；跨玩家查询、交易或大规模编队排程出现后，再拆为独立的 `PlayerArmy` 集合即可。

## 真实兵力约束

`armyRoster` 保留为账号总量。每次从模板创建实际参战部队时，服务端会按模板配比购入对应的真实士兵：原子扣除 `Σ(兵种人数 × ArmyUnitType.costKP)` 知识点，同时把新兵计入 `armyRoster` 并写入 `combatArmies`。实际可用量按下式计算：

```text
可用真实士兵 = armyRoster 总量 - Σ combatArmies 已分配数量
```

创建实际参战部队时，服务端根据模板百分比做最大余数分配，按兵种单价结算知识点，并以用户文档的 `updatedAt` 做乐观并发校验，避免两个并行操作重复扣点或覆盖对方的编组。解散该部队后，对应真实士兵回到未分配库存，知识点不返还。围城发起、支援校验和围城 PVE 初始化都只读取 `combatArmies`，不会把未编成部队的库存直接带入战斗。

## 训练营约束

- 训练部队完全不读取 `armyRoster` 或 `combatArmies`。
- 每一支训练部队的总人数上限为 `10,000`。
- 不同训练部队互不争夺虚拟兵力；同一种兵可以同时出现在多支训练部队中。
- 训练营加载 `trainingArmies`；部署、编辑、阵营切换、技能配置与坐标变化会自动保存，退出训练营时会再次强制保存。

## 接口责任

| 接口 | 责任 |
| --- | --- |
| `GET /army/me` | 返回可用真实士兵、账号总兵力和实际参战部队 |
| `POST /army/combat-armies` | 按模板和总人数扣知识点、购入真实士兵并创建实际参战部队 |
| `DELETE /army/combat-armies/:armyId` | 解散实际参战部队，将真实士兵释放回未分配库存（不退款） |
| `GET /army/training/init` | 返回训练场专用的虚拟库存和持久化训练部队 |
| `PUT /army/training/armies` | 原子替换当前用户的训练部队快照，服务端验证每支不超过一万人 |

## 兼容与迁移

新增字段默认均为空数组，所以已有用户无需离线迁移：旧的 `armyTemplates` 和 `armyRoster` 会原样保留。已有玩家需要在兵营中从模板创建至少一支 `combatArmies` 后，才能以该部队进入新的围城战斗入口。
